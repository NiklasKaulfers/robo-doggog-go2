# Local SQLite log outbox

The Go2 usually runs offline. Its log is therefore saved on the dog first and uploaded later to a NoSQL store (DynamoDB or MongoDB), when there is a connection. The app writes every log record into a local SQLite file, the **log store** (outbox). Each record has a **pushed** flag that is set only after the backend confirmed the upload (`code/src/logging/`).

**Why SQLite.** It survives crashes without extra code. WAL mode keeps committed transactions after an app crash, and `synchronous=NORMAL` avoids an fsync per commit; on a power loss only the last commits can be lost, and the file stays consistent. It handles "fetch the oldest unpushed, mark these pushed, delete the oldest" with one index on `(pushed, id)`. It needs nothing installed on the Jetson host: the build uses the system library where there is one, otherwise the official amalgamation, fetched at configure time and pinned by hash. Rejected: append-only JSON-lines files, which need hand-written rotation, a separate pushed-offset file and crash-safe rewrites; an embedded key-value store, which is one more dependency and gives no ordered queries.

**Two timestamps.** Each record has the wall clock (epoch ms) for lining events up with the real world. It also has the steady clock (ns), because the Jetson's wall clock is wrong when NTP never synced offline, and it can jump when it finally does. Ordering and durations within a run use the steady clock (and the sequence number). Correcting the wall clock afterwards is possible because both are kept.

**Upload key `deviceId#sessionId#seq`.** `seq` is the row id. It is `AUTOINCREMENT`, so ids are never reused after old records are deleted. The session id is random per app start, and the device id comes from `ROBO_DEVICE_ID`, else the hostname. Together they are unique across dogs and runs. They also stay stable when a batch that partly arrived is sent again, so the key works as DynamoDB key or MongoDB `_id` and retries are idempotent. The device id is saved per record (a `device_id` column), not taken from the dog's current configuration at upload time. Otherwise renaming a dog would change the keys of records that are not uploaded yet.

**Eviction.** The store is capped by used bytes: `(page_count − freelist_count) × page_size`. Freed pages are reused, so no `VACUUM` is needed; the WAL file can add a few MB on top. Over the cap, the oldest pushed records are deleted first, because they are already safe in the central store. Next go the oldest unpushed debug/info records: recent context matters more than old. Unpushed warnings and errors are the audit trail of safety events (`code/Agents.md` §7, §8), so they are deleted only as a last resort, oldest first. Even then the cap holds, because a full disk would lose everything. The in-memory queue protects them the same way: when it is full, a warning or error pushes out the oldest queued debug/info record. Only a queue holding nothing but warnings refuses new ones. Every eviction, and every record the queue drops, leaves a warning record with the count, so gaps in the log are visible.

**Consequences.** Logging never touches the disk on the caller's thread. A bounded queue is written by one background thread every ~500 ms, so a crash can lose the last half second. A broken store turns the logger into console-only output, and the robot keeps running. Adding a backend means implementing `Uploader::upload` and calling `shipPending`, which stops at the first failed batch.
